# Product Requirements Document (PRD)

## Smart Priority-Based Cab & Auto Allocation System

**Document purpose:** Product and implementation specification for
building a working prototype simulation in Antigravity IDE.

## 1. Product Summary

Build a web-based simulation of a smart cab and auto allocation system.
Multiple passengers can submit ride requests at the same time. The
system ranks requests using transparent priority rules, finds an
available vehicle with sufficient seating capacity, considers road-based
ETA, and assigns the most suitable vehicle. If no suitable vehicle is
available, the request enters a waiting queue and is reconsidered when a
vehicle becomes available.

The prototype is a simulation. Vehicle locations and movement are
generated by the application; they are not real driver GPS feeds or live
ride-hailing bookings.

## 2. Problem Statement

Commuters can face long waits, cancellations, unpredictable arrival
times, and difficulty finding an affordable, available vehicle during
peak hours or in crowded areas. Senior citizens may need additional
consideration, women travelling at night may have additional safety
concerns, and groups need vehicles with sufficient capacity. The
prototype explores whether priority-aware, capacity-aware allocation and
live route visibility can make the booking process more organized and
transparent.

## 3. Goals

1.  Demonstrate simultaneous booking requests from multiple passengers.
2.  Apply configurable priority rules for senior citizens and women
    during defined night hours.
3.  Prevent suitable requests from being ignored indefinitely by
    increasing priority with waiting time.
4.  Match requests only with available vehicles that have enough seats.
5.  Prefer suitable vehicles using road ETA, not just straight-line
    distance.
6.  Show vehicle assignment, route, estimated pickup time, and trip
    status on an interactive map.
7.  Demonstrate waiting-queue handling and automatic reallocation.
8.  Provide an admin view of the simulation and its current state.

## 4. Non-Goals

The prototype will not: - Connect to real taxi/auto fleets or real
driver GPS devices. - Process payments or real fares. - Guarantee
personal safety or verify a passenger's identity. - Provide emergency
response or law-enforcement services. - Claim production-grade route
accuracy, traffic-aware ETA, or dispatch reliability. - Use actual
passenger demographic data; demo profiles are synthetic.

## 5. Target Users and Interfaces

### Passenger interface

-   Create a booking by selecting pickup and destination.
-   Select vehicle type: cab or auto.
-   Enter passenger count.
-   Select a demo passenger profile/category.
-   View booking status, assigned vehicle, route, and pickup ETA.
-   Cancel a booking in eligible states.

### Driver/vehicle simulation interface

-   View assigned booking and pickup/destination.
-   View simulated vehicle status.
-   No real driver account or device tracking is required.

### Admin dashboard

-   View all active bookings and the waiting queue.
-   View available, assigned, and on-trip vehicles.
-   Start, pause, reset, and adjust simulation speed.
-   Trigger predefined demo scenarios.
-   Inspect why a request received its priority and why a vehicle was
    selected.

## 6. Core Functional Requirements

### FR-1: Booking creation

-   The user can select or enter pickup and destination locations on the
    map.
-   The user can select cab or auto and passenger count.
-   The system validates required fields and passenger count.
-   A successful request receives a unique booking ID and `requested`
    status.

### FR-2: Priority calculation

Priority must be calculated on the server using configurable rules.

Suggested prototype scoring model:

  Factor                                                            Suggested score
  --------------------------------------------- -----------------------------------
  Senior citizen                                                                +40
  Woman booking during configured night hours                                   +30
  Waiting time                                    +1 per full minute, capped at +30
  Regular passenger                                                              +0

`priorityScore = categoryBonus + waitingTimeBonus`

-   Night hours must be configurable, for example 22:00--06:00.
-   The system must explain the score components in the admin view.
-   Waiting-time points must be capped and the cap must be configurable.
-   Equal scores are resolved by earliest booking time, then booking ID.
-   These values are prototype assumptions for demonstration, not
    validated policy or a claim of legal compliance. They should be
    adjustable and reviewed for fairness before real-world use.

### FR-3: Vehicle eligibility and matching

A vehicle is eligible only if: - Its status is `available`. - Its
vehicle type matches the request, if vehicle type selection is
enforced. - Its seating capacity is greater than or equal to passenger
count.

For eligible vehicles: 1. Obtain road route and ETA from OSRM. 2. Rank
vehicles by shortest road ETA. 3. Select the best eligible vehicle for
the highest-ranked waiting request. 4. If route service fails, use a
documented fallback estimate and label it as estimated. 5. Reserve the
selected vehicle on the server before confirming assignment.

The allocation engine must avoid assigning one vehicle to multiple
active bookings.

### FR-4: Waiting queue

-   If no eligible vehicle is available, set booking status to `queued`.
-   Display queue position and current priority score.
-   Re-evaluate queued requests when a vehicle becomes available, a
    booking is cancelled, or an admin triggers reallocation.
-   Recalculate waiting-time priority before each allocation cycle.
-   Do not promise a pickup ETA when no vehicle has been assigned.

### FR-5: Route and map display

-   Render a map centered on a configurable Bengaluru demo area.
-   Show distinct markers for passengers and vehicles.
-   Show a route from assigned vehicle to pickup.
-   After pickup, show a route from pickup to destination.
-   Display route distance and estimated duration when provided by OSRM.
-   Use a distinct visual style for available, assigned, and on-trip
    vehicles.
-   Provide a legend and marker popups with IDs and statuses.

### FR-6: Vehicle movement simulation

-   Animate vehicle markers along the route geometry.
-   Movement speed must be adjustable for presentation purposes.
-   When a vehicle reaches pickup, update booking to `on_trip` (or show
    an intermediate `arrived` state if implemented).
-   When it reaches destination, mark booking `completed` and return the
    vehicle to `available`.
-   Trigger the queue allocation cycle after the vehicle becomes
    available.
-   Pause/resume must stop and continue movement without resetting
    progress.

### FR-7: Real-time updates

Use Socket.IO to broadcast: - Booking creation and status changes. -
Vehicle location and status changes. - Queue changes. - Simulation
pause/resume/speed changes.

The backend is the source of truth. The frontend should render server
updates rather than independently deciding allocation outcomes.

### FR-8: Admin monitoring

Display: - Total bookings. - Assigned, queued, completed, and cancelled
bookings. - Available, assigned, and on-trip vehicles. - Current queue
ordered by priority. - Allocation details and priority breakdown. -
Simulation controls.

### FR-9: Demo scenarios

Provide one-click scenarios such as: - Normal daytime demand. -
Peak-hour high demand. - Night-time bookings including women
passengers. - Senior citizen booking during high demand. - Group booking
requiring a larger vehicle. - Vehicle cancellation/unavailability and
queue reassignment.

## 7. Booking and Vehicle State Models

### Booking states

``` text
requested
   |
   +---- eligible vehicle found ----> assigned
   |                                    |
   |                               vehicle to pickup
   |                                    |
   |                                  arrived
   |                                    |
   |                                  on_trip
   |                                    |
   |                                 completed
   |
   +---- no eligible vehicle -------> queued
                                        |
                                  vehicle available
                                        |
                                     assigned

requested / queued / assigned -----> cancelled
```

### Vehicle states

-   `available`
-   `assigned`
-   `to_pickup`
-   `on_trip`
-   `offline`

A vehicle may have only one active booking at a time.

## 8. Data Requirements

### User

-   `id`, `name`, `category`, `createdAt`
-   `category`: `senior`, `woman`, or `regular`
-   Demo users should be synthetic.

### Vehicle

-   `id`, `vehicleType`, `location`, `capacity`, `status`,
    `currentBookingId`

### Booking

-   `id`, `userId`, `vehicleId`, `pickup`, `destination`
-   `passengerCount`, `vehicleType`, `status`
-   `priorityScore`, `priorityBreakdown`
-   `routeGeometry`, `routeDistanceMeters`, `estimatedPickupMinutes`
-   `createdAt`, `updatedAt`

## 10. User Experience and Visual Direction

-   Build a clean, modern dispatch dashboard.
-   Primary screen should emphasize the live map.
-   Include a booking form, booking list, waiting queue, and compact
    statistics.
-   Use consistent status colours and a visible map legend.
-   Provide clear empty, loading, error, and no-vehicle-available
    states.
-   Make the interface responsive for desktop presentation and smaller
    screens.
-   Keep the visual design consistent across passenger, driver, and
    admin views.

## 11. Reliability and Edge Cases

-   Reject bookings with invalid coordinates or passenger counts.
-   Reject requests when the requested vehicle type cannot support the
    passenger count.
-   Prevent double assignment during simultaneous booking requests.
-   Handle OSRM timeouts and invalid routes with a visible fallback
    state.
-   Handle vehicle going offline or being cancelled before pickup by
    releasing/reassigning the booking safely.
-   Ensure completed or cancelled bookings no longer occupy a vehicle.
-   Reconnect Socket.IO clients and refresh the current state after
    reconnection.
-   Keep the simulation reset deterministic for repeatable
    demonstrations.

## 12. Acceptance Criteria

The prototype is considered complete when:

1.  A user can create a booking with pickup, destination, category,
    vehicle type, and passenger count.
2.  At least five bookings can be created close together and processed
    without duplicate vehicle assignments.
3.  Senior citizen and configured night-time priority rules affect queue
    ordering.
4.  Waiting time changes priority according to the configured scoring
    rule.
5.  A vehicle with insufficient capacity is never assigned.
6.  The selected vehicle is eligible and chosen using road ETA where
    routing succeeds.
7.  The map displays multiple users and vehicles with a visible route
    for assigned bookings.
8.  Vehicle markers animate along routes and booking states update
    through the trip lifecycle.
9.  Unmatched requests enter a queue and are reconsidered when a vehicle
    becomes available.
10. The admin dashboard reflects current bookings, vehicles, and queue
    state.
11. Pause, resume, speed adjustment, and reset work reliably.
12. The demo can be repeated using predefined scenarios.

## 13. Recommended Build Milestones

1.  **Foundation:** Project structure, frontend layout, Express server,
    MongoDB connection, seed data.
2.  **Map:** Leaflet map, Bengaluru demo coordinates, passenger and
    vehicle markers.
3.  **Routing:** OSRM integration, route drawing, distance and ETA
    display.
4.  **Booking:** Booking API, booking states, passenger and vehicle data
    models.
5.  **Allocation:** Priority calculation, capacity filtering, road-ETA
    matching, safe vehicle reservation.
6.  **Simulation:** Vehicle animation, trip lifecycle, queue retry and
    reassignment.
7.  **Real-time:** Socket.IO events and live dashboard synchronization.
8.  **Admin and polish:** Statistics, scenario controls, responsive UI,
    error handling, acceptance testing.
